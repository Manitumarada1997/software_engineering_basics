# How LLMs Generate Text

## The most important page in this track

Everything so far converges here. Question: **"Why is the sky blue?"** — trace the *entire* loop, step by step, with every step a page you've already read.

## The full loop, step by step

```text
1. Your text:        "Why is the sky blue?"
2. Tokenization:     [Why,  is,  the,  sky,  blue, ?]          (Tokens page)
3. Token IDs:        [2418, 374, 275, 6766, 5635, 30]
4. Embedding lookup: each ID -> its vector                      (Embeddings page)
5. Transformer layers: every token attends to every earlier token
   (attention), positions added, feed-forward processing,
   layer after layer                                              (Transformer page)
6. Output: a probability for EVERY token in the vocabulary
   as the next one — one distribution, summing to 1:
       " The" 0.31 · " Light" 0.02 · " Sunlight" 0.04 ...        (Probability page)
7. Sampling: pick one (weighted dice roll — usually a high one)
8. Append the chosen token; GO TO STEP 5 with the longer sequence
9. Repeat — until a special "stop" token is sampled
10. Detokenize the whole sequence: your answer, one piece at a time
```

Read step 8 twice: **the model's own output is fed back as its input.** Every word of an answer is generated by re-reading everything so far and predicting one more piece. A 500-token answer is 500 loops of this cycle.

## Why does predicting next-tokens produce something that looks like understanding?

Because **predicting well requires modeling the thing that produced the text.** To predict the next word of a physics explanation, you must (internally, implicitly) track what's being explained. To continue a proof, code, or argument, patterns of logic must be encoded somewhere in the weights. Training on internet-scale text forced billions of weights to encode grammar, facts, styles, argument structures, code idioms — because that's what reduces next-token loss. Nothing *set out* to store knowledge; storing it was the best compression strategy.

The honest framing: understanding *of language's regularities* — built as a side effect of prediction. Whether that constitutes "real" understanding is philosophy; the engineering fact is that prediction-at-scale yields systems that converse, code, and reason passably — and hallucinate (Limits page, soon).

## Sampling — the dials you'll operate

How the "pick" in step 7 happens is a *configuration*, not a mystery:

| Dial | Effect |
|---|---|
| **Temperature** | 0 = always the top token (deterministic-ish, dull); higher = flatter distribution (creative, riskier). The Probability page's "adventurousness" dial. |
| **Top-p / top-k** | sample only from the top p% of probability mass — prune the absurd tail |
| **Stop conditions** | max tokens, stop sequences — your resource limits |

Same prompt, different answers = the dice rolls differing — non-determinism by design, controllable by temperature, but never fully eliminable while sampling.

## The KV cache — one efficiency secret, previewed

Step 8's naive version re-processes the whole conversation each loop — wasteful, since earlier tokens' attention results never change. Real systems cache them (the **KV cache**) and process only the new token. This is *the* central optimization of inference — full treatment on the Serving page, but you now know why it exists.

## The DevOps mapping

| Generation | Your world |
|---|---|
| One token per forward pass | a strictly sequential pipeline stage — the parallelism lives *inside* each pass |
| Sampling dials | tuning knobs with QPS/latency tradeoffs — config, not code |
| Stop conditions | resource limits — the runaway-generator guard |
| Feedback loop | a reconciler feeding its own output back — state grows each iteration |

## Remember This

1. Generation = loop: embed → transform → distribution → sample → append → repeat
2. The model re-reads its own output; an answer is hundreds of cycles
3. Prediction-at-scale forced knowledge into the weights — compression as understanding
4. Temperature/top-p are operational dials; non-determinism is by design
5. KV caching avoids reprocessing history — the key inference optimization

## One Sentence

An LLM answers by repeatedly converting everything so far into a probability distribution over the next token and sampling from it — and it appears to understand because predicting language well required encoding how the world's text behaves.
